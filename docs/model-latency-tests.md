# 模型应答延时测试

在新建任务或已有任务的模型下拉菜单中，先读取模型列表并选择一个明确的模型，再点击“应答延时测试”。选择默认模型时，必须由该环境的原生目录返回实际默认模型 ID；无法解析时先明确选择模型。

测试前确认执行环境、引擎、模型和账号/API。每次只向当前选中的模型发送一条要求回复 `OK` 的请求，可能消耗额度。测试使用独立的只读原生会话，不续接当前任务历史、附件或硬件授权；CLI 仍可能加载目标目录的项目指令和原生工具配置。

等待上限默认 180 秒，可选 60、120、180、300 或 600 秒。该上限约束本次测试从启动到完成的等待，普通任务对话的超时及引擎原生配置不受影响。“测试列表模型”继续逐项检查完整列表，维持每项 25 秒的快速测试上限。

结果分别显示首次可见回复和总耗时。计时从单个模型测试开始，包含 CLI 启动、连接和原生重试；它不是 OpenAI HTTP 首字节时间。支持文本片段的引擎记录首个非空模型回复片段；仅返回整段文本时显示完成文本的观测时间。连接提示、日志、工具记录和用量通知均不当作模型回复。

超过一分钟尚无回复时可以继续等到所选上限，也可以停止。已收到首段回复后又失败或超时，仍保留首次观测时间；没有观测到文本时明确显示未收到回复，不以总耗时冒充首次时间。超时只说明本次测试未在上限内完成，不证明模型一直不可用。

MiMo 的专用 API 测试使用非流式请求，只能报告完整调用耗时，暂不提供首次可见回复延时测试。切换任务、环境或账号后，旧测试的异步结果不会覆盖新目标。

出现服务繁忙、429 或响应流断开时，结果会区分错误类型。增加测试等待上限不能阻止服务端主动拒绝或关闭连接，也不会更改 Codex provider 的内部网络超时。
