# Codex 原生接入：权限与审批

Duo的 Codex 任务现在通过目标环境里的 `codex app-server`（stdio JSON-RPC）执行。Claude Code 的执行通道不变。不要向局域网开放 app-server 端口；远程入口仍是Duo自身的登录与 CSRF 保护接口。

## 模式

| 模式 | 沙箱 | 原生审批策略 | 审批人 | 网络 |
| --- | --- | --- | --- | --- |
| 请求批准 | workspace-write | on-request | user | 默认允许；自定义模式可关闭 |
| Codex 自动审批 | workspace-write | on-request | auto_review | 默认允许；自定义模式可关闭 |
| 只读分析 | read-only | never | user | 关闭 |
| 完全访问 | danger-full-access | never | user | 允许 |

“自动审批”仍保留沙箱，由 Codex 原生风险评审处理需要升级权限的请求，不是全部放行。可用性受 CLI、账号与管理策略影响；失败不会静默回退到完全访问。只读模式故意不允许升级权限。`never` 的含义是不请求批准，不是授予所有权限。

工作区模式继续沿用Duo已有的默认联网行为，**不是官方默认的离线工作区**。离线模式显式下发 `networkAccess=false`，不会因 CLI 全局配置已有 `true` 而失效。需要网络或越界时，交互模式可继续请求临时批准。

知识总结强制使用只读、不联网、无任务硬件工具的权限，不继承会话的完全访问模式，也不改变下一轮对话已选的工作模式。

## 交互与生命周期

- 保留并恢复精确的原生 thread ID；每轮使用 thread/start 或 thread/resume，再调用 turn/start。
- 模型、推理强度、工作目录、沙箱与审批配置直接传给原生协议。
- 网页显示命令、文件修改、临时文件/网络权限申请及补充问题。待处理卡片不受执行轨迹折叠影响。
- 批准仅响应当前原生请求，不写永久命令规则。临时权限只使用原始申请内容，范围固定为当前轮次，不接受浏览器提交额外权限。
- 请求按任务、执行轮次与原生请求身份关联；回答一次后失效。刷新可重新看到仍在等待的请求，但重启、断连或已结束的请求不会自动重放授权。
- 停止先调用 turn/interrupt；未及时结束时再清理执行进程。中断确认与终态分开，异常断流不能当成完成。
- v0.22.14 起，在 Duo 启动的 Codex 进程中设置 `features.default_mode_request_user_input=true`，允许普通模式使用原生提问工具；不写用户全局配置。卡片支持原生选项及允许的自由输入，`isBlocking=false` 显示为可继续工作的补充问题。是否发起问题仍由模型决定。
- 执行中可以选择“立即引导”“中断后发送”“排队发送”。立即引导只发送文字，通过 `turn/steer` 和 `expectedTurnId` 定位当前轮次，不变更模型或权限；确认接收后记录用户消息。浏览器重试使用相同请求标识，未知结果不自动改为排队。
- 异步提问卡片的「提交答案」自动选择立即引导当前执行；没有活动轮次时才继续新一轮。原生确认、答案记录和问题完成状态一并持久化。接收状态不明时保留原答案与投递记录，不改为排队，防止重复发送；明确拒绝时允许重试。
- 中断后发送先入库，再取消当前运行；沿用原 thread ID，等待旧运行退出后优先处理新要求，保留其他排队消息。停止按钮继续取消当前运行及所有排队消息。若旧进程退出无法确认，停止后续队列并显示原因。
- WSL 使用明确的发行版/用户，SSH 使用既有主机校验；不把 Windows 的受限工具环境传给 WSL。
- 硬件授权仍由任务的设备授权控制。Codex 自动审批不能创建新的串口或继电器授权；运行令牌通过管道/子进程环境传递，不放入命令行、提示词或全局配置。

## 本阶段边界

本阶段是原生任务与审批通道的替换，不声称完整复制官方客户端：

- 每轮独立运行 app-server，通过原生 thread ID 连续对话；执行中的连接支持 steer，没有跨轮常驻连接或“会话永久允许”操作。
- 模型选择器优先使用目标环境的原生 `model/list`，并在界面显示读取来源与错误。
- 飞书仍可提交任务，但原生待审批请求需要进入Duo网页处理；没有新增飞书交互审批卡。
- 暂不支持的 MCP 表单会明确拒绝，不伪造成功。编辑器专属功能、逐 token 渲染与完整官方工具卡片尚未对齐。
- 目前只处理本任务主线程的审批；子线程的独立审批拒绝放行，不会误绑定到主线程。
- 账号登录仍由各执行环境的 Codex CLI 管理，Duo不复制或显示令牌。

## 验证与使用

Go 回归测试通过模拟 app-server 子进程验证，不使用真实付费模型、不连接实体硬件。前端新增 `scripts/Test-Codex-Approvals-Web.mjs`，并保留原有工作台/对话测试。构建前执行 TypeScript 检查、前端构建和 `go test ./...`。

v0.22.14 的 `codex_steer_test.go` 覆盖原生轮次校验、拒绝/错误确认/结束前未确认、HTTP 重试去重、中断后的顺序与会话恢复、未确认退出时停止队列；`scripts/Test-Live-Interaction-Web.mjs` 覆盖原生选项提交、非阻塞问题、发送失败、附件边界和切换任务后的草稿隔离。问题与引导 schema 对照本机 Codex 0.153.4 生成，真实模型调用、WSL/SSH 端到端效果仍需日常使用验证。

真实任务验收建议：选择 WSL 项目，使用“请求批准”执行一个工作区内的文件修改；再明确要求读取或写入一个工作区外的测试目录，确认网页出现原生申请。分别验证拒绝、批准、停止、刷新以及恢复原生会话。不要用重要数据或设备上下电测试完全访问模式。

参考：[Codex app-server](https://learn.chatgpt.com/docs/app-server)、[原生审批与安全](https://learn.chatgpt.com/docs/agent-approvals-security)。协议字段已对照本机 CLI 生成的 v2 schema，而非只依赖文档示例。
